1. 先看清要造什么：记忆助手的四步闭环

我们要造的不是「向量库 Demo」，而是一个闭环系统。把它拆成四步，后面每一步都对应一个具体能力：

步骤发生什么由谁承担
① 采集原始文档/对话变成结构化 SourcePowerContext Source
② 派生Source 被处理成可检索的 Memory 条目PowerContext 后台处理
③ 检索按查询同时走向量与全文seekdb 混合检索
④ 沉淀本次结论写回，形成下一轮的输入PowerContext 记忆
分工要清楚：seekdb 负责「把相关的东西找出来」，PowerContext 负责「把值得记住的东西记下来」。 这两条线各自都能单独跑，但只有接起来，第 ④ 步才会产生复利。

2. seekdb 概念与上手：向量、全文与混合检索

2.1 它是什么

seekdb 是兼容 MySQL 协议的新一代数据库，把向量检索、全文检索和结构化条件放进同一个 SQL 执行引擎里。 对你的价值是：不需要「业务库 + 向量库」两套系统，也不需要在应用层把两路结果手工拼起来。

2.2 起一个实例

# 最省事：官方包
docker run --name seekdb -p 2881:2881 -d oceanbase/seekdb:1.4.0

# 或者本地 server 模式（Windows / Linux 都可）
./seekdb --nodaemon --parameter memory_budget=4G --parameter cpu_count=4

起来后用任意 MySQL 客户端连 127.0.0.1:2881，用户 root，空密码。

2.3 建表、灌数据、混合检索

CREATE DATABASE kb;
USE kb;

CREATE TABLE docs (
  id        BIGINT PRIMARY KEY AUTO_INCREMENT,
  title     VARCHAR(256) NOT NULL,
  body      TEXT NOT NULL,
  embedding VECTOR(4)
);

INSERT INTO docs(title, body, embedding) VALUES
  ('连接池配置', 'max_connections 建议按峰值 QPS 的 1.5 倍设置', '[0.1,0.2,0.3,0.4]'),
  ('慢查询',   '没有走索引的排序会退化成全表排序',           '[0.9,0.1,0.2,0.3]');

-- 全文检索：关键词
SELECT id, title FROM docs WHERE MATCH(title, body) AGAINST('索引');

-- 向量检索：语义相近
SELECT id, title FROM docs
  ORDER BY l2_distance(embedding, '[0.9,0.1,0.2,0.3]') APPROXIMATE
  LIMIT 5;

-- 混合：结构化条件 + 向量 + 全文，一起交给 seekdb
SELECT id, title
  FROM docs
  WHERE MATCH(title, body) AGAINST('索引')
  ORDER BY l2_distance(embedding, '[0.9,0.1,0.2,0.3]') APPROXIMATE
  LIMIT 5;
注意 APPROXIMATE：它是近似的 HNSW 检索，召回率与延迟之间有取舍。 需要严格一致时用精确检索（去掉 APPROXIMATE），并用真实 Recall 指标验证质量没有退化。

2.4 全文索引：建索引前先知道自己在建什么

-- 中文用 ik 分词器，英文用 beng
ALTER TABLE docs ADD FULLTEXT INDEX ft_title (title) WITH PARSER ik;

SHOW CREATE TABLE docs\G   -- 看索引建好没、字段对不对

3. PowerContext 概念与上手：Scope、Source、Memory

3.1 它是什么

PowerContext 是 AI 应用的记忆与上下文层。它把「数据」和「记忆」分开： Source 是原始输入（文档、对话、日志），Memory 是从 Source 里提炼出来、可被检索复用的结论。 后台处理负责把 Source 变成 Memory，你不需要自己写提炼流水线。

3.2 核心概念

概念是什么你会怎么用
Scope一个隔离的上下文空间按系统 / 按服务 / 按用户分 scope，记忆不会串
Source原始内容，带类型与元数据入库的文档、一次会话、一条告警
Memory从 Source 提炼的可检索条目召回后直接进提示词
Artifact记忆的物化载体（memory / topic-memory / handoff …）通常不需要直接碰
处理Source → Memory 的后台任务配置触发方式：按条数触发或按时间触发

3.3 三种接入方式

# 1) HTTP API
POST /v1/scopes/{scope_id}/sources
POST /v1/scopes/{scope_id}/memories/search

# 2) MCP（推荐给 Agent 用，工具语义更直接）
#    capture_content_source / search_memory

# 3) Python SDK
from powercontext.client import PowerContextClient
async with PowerContextClient("http://127.0.0.1:8000") as c:
    await c.capture_content_source(request)
    await c.search_memory(request)

3.4 把「自动处理」打开

# 新增来源达到阈值就触发一次记忆处理（比等定时轮询更快）
runtime:
  memory_source_count_threshold: 1

# 或者按固定周期处理
runtime:
  memory_schedule_seconds: 30

4. 动手：把两者接起来

4.1 数据面：文档与向量存 seekdb

业务原文与向量放 seekdb：向量字段建索引，全文字段建全文索引，检索一次搞定。

CREATE TABLE kb.docs (
  id        BIGINT PRIMARY KEY AUTO_INCREMENT,
  title     VARCHAR(256) NOT NULL,
  body      TEXT NOT NULL,
  embedding VECTOR(4),
  KEY ft_body (body) WITH PARSER ik
);

4.2 记忆面：结论存 PowerContext

每次排查完，把「问题 → 根因 → 证据 → 处置」写回 PowerContext，下次直接召回。

from powercontext.client import PowerContextClient
from powercontext.client.client import CaptureContentSourceRequest

async with PowerContextClient("http://127.0.0.1:8000") as c:
    await c.capture_content_source(CaptureContentSourceRequest(
        scope_id=scope_id,
        source_id=f"incident-{ticket_id}",
        content="现象：... 根因：... 证据：EXPLAIN ... 处置：...",
    ))

4.3 检索时合并两路

一个查询同时要「语义相近」和「关键词命中」时，让 seekdb 出混合结果， 再用 PowerContext 召回历史结论补上下文：

-- 第一路：seekdb 混合检索（语义 + 关键词 + 结构化条件）
SELECT id, title, body FROM kb.docs
 WHERE MATCH(title, body) AGAINST('索引')
 ORDER BY l2_distance(embedding, :query_vec) APPROXIMATE
 LIMIT 5;

-- 第二路：PowerContext 召回历史结论
hits = await c.search_memory(SearchMemoryRequest(scope_id=scope_id, query=q, limit=5))

4.4 验证它真的在工作

别只看「跑通了」。三个必须实测的点：

验证项怎么做合格线
检索质量固定评测集跑 Recall@10 / nDCG@10与基线持平或更好
记忆真的被用上写入一条记忆 → 新会话提问 → 看是否召回能召回且答案引用了它
新增内容可被检索写入 → 等索引刷新 → 检索能命中新增内容

5. 用 Qoder 把它变成产品

Qoder 的价值在这个项目里非常具体：它把「查文档、读代码、跑起来、再迭代」这条闭环压缩成对话。 下面每一步都可以直接交给 Qoder 执行。

5.1 让 Qoder 先摸清地形

# 给 Qoder 的第一句
请阅读 seekdb 仓库的 docs 与 PowerContext 的 docs，
列出：1) 建混合检索需要的最小表结构；2) 记忆写入与召回的完整接口；
3) 我本地已经跑起来的 seekdb 实例该怎么连。不要改代码，先给方案。

5.2 让它搭最小闭环

按上面的方案实现一个最小可跑版本：
- 一个 /search 接口，入参 query 和 top_k
- seekdb 出混合检索结果，PowerContext 召回历史结论，两路合并后返回
- 每条结果标注来源（文档 / 记忆）
- 补一个可以一键跑的 seed 脚本和一个 smoke test

5.3 用它做性能与质量迭代

把「优化」这件事也交给 Qoder，但要给它可验证的目标，否则它只会改代码：

在固定评测集上对比三种实现，记录 Recall@10 与 p50 延迟：
A) 纯向量   B) 纯全文   C) 混合
要求 C 的 Recall 不低于 A，p50 不高于 A 的 1.5 倍。
把结果写成表格，只改真正有收益的那一项。

5.4 提示词：让 Agent 知道自己是谁

你是一个数据库排查助手。
回答时：
- 涉及数据库结论时，区分「本次实测」和「历史记忆」，不要混为一谈；
- 历史记忆只在当前实例上验证过之后才可作为结论；
- 没有依据的信息写「未核实」，不要编造；
- 给结论时附上可复现的 SQL。

6. 踩坑清单与收尾

坑表现处理
APPROXIMATE 悄悄掉召回线上「搜不到」用评测集量化 Recall，别凭感觉
记忆把旧结论当真给出过时的处置建议召回只当线索，落地前复核
索引没刷新就检索新增内容搜不到检索前确认刷新策略（写入后可见）
Scope 用混记忆串味按系统/服务分 scope，别共用
把密钥写进记忆凭据泄漏记忆只存结论与证据
收尾自查

  2. seed 脚本能造出可检索的数据与一条可召回的记忆 ✓
  3. smoke test 一条命令跑通「写入 → 召回 → 检索」 ✓
  4. 有一张 before/after 的质量与延迟对比表 ✓
